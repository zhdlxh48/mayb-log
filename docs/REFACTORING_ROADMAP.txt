# mayb-log 최종 리팩터링 및 기능 개선 작업 지시문

## 0. 프로젝트와 작업 원칙

대상 저장소:

`zhdlxh48/mayb-log`

분석 당시 `main` HEAD:

`e9342ce8c1084dd8f073b223faa50f7bc2f44282`

커밋 메시지:

`chore: merge feature/quality-handover into main`

이 커밋의 GitHub Actions `Verify and deploy` workflow는 분석 당시 `build`, `deploy` 모두 성공한 상태였다.

작업을 시작하기 전에 반드시 현재 `main` HEAD와 working tree를 다시 확인하라.

분석 당시 기준 커밋 이후 변경사항이 존재한다면 무시하거나 덮어쓰지 말고 먼저 diff를 파악하여 이번 작업과 충돌하지 않는지 확인한 다음 진행하라.

이번 작업의 목적은 기존 사이트를 새롭게 디자인하는 것이 아니다.

현재 블로그의 시각적 철학은 다음과 같다.

* 5ch
* 2chan
* Hacker News
* Hada News

와 같은 단순하고 정보 밀도가 높으며 장식이 적은 인터페이스를 현대적인 데이터 구조와 Astro 구현 방식으로 표현한다.

따라서 다음과 같은 전형적인 SaaS/웹앱 스타일로 바꾸지 마라.

* 불필요한 카드 UI
* 과도한 border radius
* 과도한 shadow
* gradient
* 의미 없는 애니메이션
* 지나치게 큰 여백
* 장식 목적의 UI 요소

기존 화면의 인상과 정보 구조를 최대한 보존하면서 **코드 구조, Tailwind 사용 방식, 콘텐츠 확장성, 검색, 테스트, 품질 도구, 문서, 유지보수성**을 개선하는 것이 목적이다.

사용자가 제공한 화면 캡처는 시각적 참고 자료일 뿐이다.

**코드와 실제 레이아웃 구조를 먼저 분석하고 코드가 source of truth가 되어야 한다.**

또한 요구사항을 억지로 충족시키기 위한 우회 구현을 하지 마라.

어떤 요구가:

* 현재 Astro 버전과 정상적으로 구성될 수 없거나
* 라이브러리 제약 때문에 요구와 다르게 동작하거나
* 더 단순하고 명확한 해결책이 명백히 존재하거나
* 프로젝트 구조를 심각하게 복잡하게 만들어야만 구현할 수 있다면

임의의 workaround를 추가하지 말고 작업을 중단한 뒤 이유와 대안을 보고하라.

# 2. Tailwind CSS를 실제 스타일링 시스템으로 사용하라

현재 Tailwind CSS와 `@tailwindcss/vite`는 설치 및 연결되어 있지만, 실질적인 스타일 대부분이 `src/styles/global.css`의 raw CSS로 작성되어 있다.

이 구조를 변경한다.

## 목표

`src/styles/global.css`는 가능한 한 다음 역할만 담당하게 한다.

* `@import "tailwindcss"`
* 필요하다면 Tailwind v4 `@theme`을 통한 사이트 디자인 token

  * background
  * foreground
  * muted
  * border
  * accent
  * 기타 실제로 필요한 색상/token
* 정말 전역으로만 표현할 수 있는 최소한의 내용

일반적인 컴포넌트 스타일이나 레이아웃 CSS를 `global.css`에 계속 작성하지 마라.

현재 존재하는 다음과 같은 대부분의 selector 기반 스타일을 Tailwind utility로 옮겨라.

* sidebar
* header
* layout
* post list
* post list item
* toolbar
* taxonomy
* archive
* post header
* post metadata
* TOC
* pagination
* author
* search form
* responsive layout
* article typography
* iframe
* link preview

## `@tailwindcss/typography`는 사용하지 않는다

Markdown/MDX 본문의 디자인 자유도를 유지하기 위해 Tailwind Typography plugin의 `prose` preset에 의존하지 않는다.

Markdown과 MDX가 생성하는 HTML 요소도 Tailwind로 스타일링한다.

예를 들면 article wrapper에서 Tailwind arbitrary descendant variant를 사용하여 다음 요소를 직접 스타일링할 수 있다.

* `p`
* `h2`
* `h3`
* `h4`
* `a`
* `ul`
* `ol`
* `li`
* `blockquote`
* `hr`
* `code`
* `pre`
* `table`
* `th`
* `td`
* `img`
* `figure`
* `figcaption`
* `iframe`
* `.link-preview`

긴 Tailwind class 집합이 article 여러 곳에서 반복된다면 `ArticleProse.astro`와 같은 의미 있는 공통 컴포넌트로 추출하는 것은 허용한다.

단순히 class 수를 줄이기 위한 무의미한 component abstraction은 만들지 마라.

## `@layer components`

기본적으로 사용하지 않는다.

동일한 스타일 패턴이 실제로 여러 컴포넌트에서 반복되고, Astro component로 추출하는 것보다 CSS component class가 더 명확한 경우에만 제한적으로 사용한다.

# 4. 게시물 본문 + TOC 전체 컨테이너를 화면 가운데 정렬하라

현재 게시물을 열면 본문과 TOC가 전체 content area의 왼쪽에 치우쳐 있다.

단순히 article body에 `mx-auto`만 적용하지 마라.

대신:

* article body
* TOC

를 하나의 desktop article container로 보고 **두 요소를 포함한 전체 grid/container 자체를 가운데 정렬**한다.

대략적인 구조는 다음과 같다.

```text
                 centered article container

        ┌──────────────────────────────────────┐
        │        article        │     TOC      │
        │        ~720px         │              │
        │                       │              │
        └──────────────────────────────────────┘
```

게시물의:

* header
* title
* subtitle
* author
* metadata

또한 본문 column의 기준선과 자연스럽게 정렬되어야 한다.

기존 desktop sticky TOC 기능은 유지한다.

모바일/태블릿에서는 기존처럼 자연스럽게 한 column으로 내려가야 한다.

화면 폭:

* 375px
* 768px
* 1024px
* 1440px

등에서 horizontal overflow가 없어야 한다.

# 5. Markdown + MDX를 모두 지원하라

게시물 포맷을 MDX 하나로 강제하지 않는다.

**`.md`와 `.mdx`를 모두 정식 콘텐츠 형식으로 지원한다.**

일반적인 글은 Markdown을 그대로 사용할 수 있어야 한다.

```text
index.md
```

컴포넌트, Link Preview, iframe, 외부 embed 등이 필요한 글은:

```text
index.mdx
```

를 사용할 수 있어야 한다.

Astro 공식 `@astrojs/mdx` integration을 사용하라.

현재 Astro 버전과 호환되는 버전을 설치하고, Astro 자체를 불필요하게 major upgrade하지 마라.

`astro.config.mjs`에 `mdx()` integration을 정상적으로 추가한다.

Astro 공식 문서가 안내하는 Content Collection glob 방식을 사용한다.

현재 posts:

```text
*/index.md
```

는:

```text
*/index.{md,mdx}
```

와 같이 `.md`와 `.mdx`를 모두 로드하도록 변경한다.

`pages` collection도 Markdown 콘텐츠를 받는 곳이라면 마찬가지로:

```text
*.{md,mdx}
```

를 지원하도록 한다.

authors/series의 YAML 구조는 변경할 이유가 없다.

## Markdown과 MDX 공통 처리

Astro MDX integration은 기본적으로 기존 Markdown configuration을 상속한다.

따라서 현재 Markdown 처리에서 실제로 필요한 다음 기능은 `.md`와 `.mdx` 모두에 일관되게 동작하도록 유지하라.

* GitHub Pages base path용 Markdown link 처리
* Markdown local image 처리
* alt validation
* responsive image 처리
* Shiki syntax highlighting

현재 custom `markdownLinks` 및 `markdownImages`가 담당하는 유효한 기능은 directive 제거와 혼동해서 삭제하지 마라.

# 6. custom Markdown directive 시스템을 완전히 제거하라

기존 custom directive 시스템은 더 이상 사용하지 않는다.

다음 문법들은 전부 폐기한다.

```text
::youtube
::link-card
::social
:::callout
:::details
:::figure
::metric
```

Markdown source에서 이 문법을 공식 기능처럼 지원하지 않는다.

## 제거 대상

현재 존재하는 directive 관련 구현을 모두 제거하라.

예:

* `remark-directive`
* `src/lib/markdown/directives.ts`
* `YouTubeEnhancement.astro`
* directive 전용 CSS
* directive 전용 테스트
* directive fixture
* directive 관련 문서
* directive 관련 build validation

`remark-directive` dependency도 제거한다.

단, `unist-util-visit`처럼 `markdownLinks`, `markdownImages` 등 다른 실제 코드에서 계속 사용하는 dependency는 directive가 없어졌다는 이유만으로 삭제하지 마라.

dependency 제거는 반드시 실제 usage 확인 후 수행한다.

# 7. MDX 확장 요소의 원칙

별도의 범용 Embed abstraction을 만들지 않는다.

다음을 만들지 마라.

```text
Embed provider registry
YouTubeProvider
TwitterProvider
VimeoProvider
GenericEmbedProvider
```

같은 구조.

새 서비스를 지원하기 위해 자체 embed framework를 만들 필요가 없다.

MDX 자체가 escape hatch 역할을 한다.

---

# 8. YouTube/Vimeo 등은 공식 iframe/embed를 직접 사용한다

서비스가 공식 iframe을 제공한다면 MDX 안에 공식 iframe을 그대로 작성한다.

예:

```mdx
<iframe
  src="..."
  title="..."
  loading="lazy"
  allow="..."
  allowFullScreen
/>
```

MDX/JSX 문법 때문에 attribute 이름의 최소한의 문법 변환이 필요한 것은 허용한다.

예:

```text
allowfullscreen → allowFullScreen
```

그러나 iframe의 UI를 다시 구현하거나 custom player UI를 만들지 마라.

YouTube의 경우:

* 실제 YouTube embed player
* YouTube controls
* 공식 iframe 방식

을 사용한다.

현재처럼:

```text
사용자 정의 재생 버튼
→ 클릭
→ JS로 iframe 교체
```

하는 구현은 제거한다.

Astro Embed의 `<YouTube>` component 등으로 다시 lite-player UI를 만들지 않는다.

사용자가 요구한 것은 **해당 서비스가 제공하는 실제 embed UI**이다.

## iframe styling

MDX 작성자가 매번 반응형 Tailwind class를 작성하지 않아도 되도록 article wrapper에서 iframe 기본 layout만 처리할 수 있다.

예:

* `max-width: 100%`
* video iframe의 적절한 aspect ratio
* border 제거
* block layout

단 서비스 UI 자체를 꾸미거나 덮어쓰지 않는다.

## 로딩

공식 iframe에서 지원하면:

```text
loading="lazy"
```

를 사용한다.

third-party embed script가 필요한 서비스의 경우 해당 script를 사이트 전체에서 global하게 항상 로드하지 마라.

그 embed가 실제로 사용되는 MDX에서만 official embed/script를 사용하고, vendor가 지원하는 `async`, `defer`, lazy 방법이 있으면 활용한다.

범용 IntersectionObserver embed framework를 미리 만들 필요는 없다.

---

# 9. X 등 iframe이 아닌 공식 embed도 공식 방식을 사용한다

서비스가 iframe 대신:

* blockquote
* official JS
* official widget script

같은 embed 방식을 제공한다면 해당 공식 snippet/방식을 사용한다.

우리 사이트가 X UI를 흉내 낸 custom card를 만들면 안 된다.

같은 service embed가 반복되면서 official script를 페이지당 정확히 한 번만 넣는 문제 등이 실제로 발생했을 때만 아주 얇은 helper/component를 고려할 수 있다.

그 경우에도 provider framework를 만들지 마라.

**실제 필요가 발생하기 전에 abstraction을 만들지 않는다.**

# 10. 일반 링크 Preview는 Astro Embed `LinkPreview`를 사용한다

일반 웹 링크를 카드 형태로 보여줄 때 자체 구현을 만들지 않는다.

사용자가 지정한 Astro Embed의 `LinkPreview` component를 사용한다.

패키지:

```text
astro-embed
```

MDX 사용 예:

```mdx
import { LinkPreview } from 'astro-embed';

<LinkPreview id="https://example.com/article" />
```

`LinkPreview`는 다음 정보를 가능한 범위에서 표현한다.

* 원본 URL
* title
* description
* Open Graph media/image
* site information

metadata 수집에 실패하거나 valid title이 없으면 Astro Embed가 제공하는 URL-only fallback을 그대로 허용한다.

## 하지 말아야 할 것

다음을 구현하지 마라.

* custom metadata scraper
* proxy server
* metadata API server
* edge function
* runtime CORS proxy
* 별도의 OG database
* custom link preview framework

Link Preview metadata가 build 시점의 정보가 된다는 trade-off는 허용한다.

새 글 작성/사이트 rebuild 시 다시 갱신되는 것으로 충분하다.

## 일반 링크와 Preview 링크를 구분한다

모든 외부 `<a>`를 자동으로 Preview card로 바꾸지 마라.

일반 Markdown 링크:

```md
[Astro](https://astro.build/)
```

는 일반 링크 그대로 유지한다.

작성자가 card가 필요할 때만 `.mdx`에서 명시적으로:

```mdx
<LinkPreview ... />
```

를 사용한다.

## Styling

Astro Embed가 제공하는 `.link-preview` 구조를 article wrapper의 Tailwind descendant selector 또는 상속 가능한 Tailwind arbitrary property로 사이트 스타일에 맞게 최소 조정할 수 있다.

그러나 custom LinkPreview HTML을 다시 구현하지 마라.

# 11. 검색을 Pagefind에서 전체 substring 검색으로 변경하라

현재 Pagefind는 `"down"`으로 `"Markdown"`을 찾는 것과 같은 arbitrary infix substring 검색 요구에 적합하지 않다.

검색 요구사항은 다음과 같이 확정한다.

**검색 가능한 콘텐츠의 모든 텍스트에서 문자열 중간도 검색되어야 한다.**

예:

```text
Markdown → down
Markdown → ark
FlexSearch → Search
abcdefgh → cde
```

앞부분 prefix만 검색하는 것이 아니다.

## 검색 대상

공개된 콘텐츠의 검색 가능한 텍스트 전체를 대상으로 한다.

게시물의 경우 최소한:

* title
* subtitle
* description
* 실제 렌더링된 body text
* tags
* categories
* series
* author names
* 기타 사용자에게 실제로 보이는 콘텐츠 관련 text

를 포함한다.

Markdown과 MDX 모두 동일하게 검색 가능해야 한다.

**MDX의 source code 자체를 검색해서는 안 된다.**

즉 다음과 같은 것은 검색 corpus에 들어가면 안 된다.

```text
import
JSX syntax
component source
iframe attributes
script source
front-end implementation noise
```

가능한 한 **사용자에게 렌더링되어 보이는 텍스트**를 검색한다.

Sidebar/navigation/footer 같은 모든 페이지에 반복되는 site chrome을 article body로 색인해서 검색 결과를 오염시키지 마라.

draft 콘텐츠는 검색 결과에 포함시키지 않는다.

기존에 공개되지만 `noindex`인 글이 내부 검색에는 포함되던 동작은 특별한 이유가 없다면 유지한다.

## FlexSearch

Pagefind를 제거하고 FlexSearch를 사용한다.

arbitrary substring 검색을 위해 FlexSearch의 full/substring matching이 가능한 tokenizer/index 설정을 사용한다.

한국어와 영문 모두 검증한다.

## 성능 격리

검색 때문에 전체 사이트가 느려져서는 안 된다.

다음을 지켜라.

* Search 관련 JavaScript는 `/search/`에서만 로드
* 일반 페이지에는 FlexSearch bundle을 싣지 않음
* 검색 corpus/index도 일반 페이지에서 다운로드하지 않음
* search page에서도 가능한 한 first input 또는 idle 이후 lazy initialization
* 현재 FlexSearch 버전에서 안정적으로 지원된다면 Web Worker에서 index 생성/검색 수행
* browser main thread를 불필요하게 block하지 않음

Worker 구현 때문에 지나치게 복잡한 custom architecture가 필요해진다면 임의 구현하기 전에 문제를 보고하라.

## 검색 데이터

별도 root `scripts/`를 이용해 search index를 만들지 않는다.

Astro build 자체에서 생성 가능한:

* static JSON endpoint
* build-time generated search data
* 또는 그에 준하는 Astro-native 구조

를 사용한다.

검색 corpus를 브라우저에서 받아 FlexSearch index를 구성하는 방식도 허용된다.

무엇을 선택하든 일반 페이지 초기 로딩에 영향을 주지 않는 구조를 우선한다.

## 검색 UX

기존 Search 페이지의 기본 UX는 유지/개선한다.

* 입력
* debounce
* 검색 중 상태
* 결과 개수
* 결과 없음
* 검색 초기화
* 오류 상태
* keyboard 접근성
* 결과 title
* 읽을 수 있는 excerpt/description
* GitHub Pages base path

를 정상 지원한다.

HTML injection이 발생하지 않도록 결과 텍스트를 안전하게 출력한다.

## 검색 테스트 필수

최소한 다음 동작을 테스트한다.

```text
Markdown
검색어: down
→ Markdown이 포함된 콘텐츠 검색 성공
```

그리고 실제 본문의 중간 문자열도 하나 테스트한다.

한국어 검색도 유지한다.

# 13. root `scripts/` 디렉터리를 완전히 제거하라

# 14. 테스트는 `tests/` 아래의 `*.test.ts`로 통일하라

테스트로 실행되는 모든 test entry file은:

```text
tests/**
```

아래에 위치하고:

```text
*.test.ts
```

이름을 사용한다.

하위 디렉터리는 구조적으로 필요하면 사용할 수 있다.

예:

```text
tests/
  unit/
    taxonomy.test.ts
    markdown.test.ts

  build/
    output.test.ts
    seo.test.ts

  browser/
    site.test.ts
    search.test.ts
```

현재:

```text
tests/browser/site.spec.ts
```

와 같은 `.spec.ts`는 `.test.ts`로 변경한다.

Playwright config도 `*.test.ts` convention과 일치시켜라.

## custom MJS test runner 제거

다음 방식은 사용하지 않는다.

```text
scripts/test-content.mjs
scripts/check-build.mjs
```

처럼 직접 만든 runner가:

* fixture project를 복사하고
* build를 spawn하고
* 여러 validation case를 반복 실행

하는 구조.

사용자가 이런 자체 test harness를 원하지 않는다.

## 무엇을 테스트해야 하는가

Astro build 자체가 이미 실패시키는 단순 schema/build 오류를 동일한 방식으로 반복해서 테스트하지 마라.

예:

* title이 필수인데 title 없는 임시 사이트를 만들어 Astro build가 실패하는지 검사

같은 테스트는 굳이 유지하지 않아도 된다.

실제 unit logic이 존재한다면 해당 logic을 직접 테스트한다.

빌드 후에만 알 수 있는 중요한 invariant는 `tests/build/*.test.ts` 같은 정상 테스트로 검사할 수 있다.

예:

* canonical
* internal links
* sitemap
* RSS
* JSON-LD
* alt
* generated image references
* search data
* expected static route

단순한 build 성공 여부는 `pnpm build`가 검증한다.

## fixtures

테스트 fixture가 정말 필요한 경우:

```text
tests/fixtures/
```

내에 정적 fixture로 둘 수 있다.

하지만 fixture를 생성하는 별도 standalone script를 만들지 않는다.

# 21. 성능을 반드시 보존하라

현재 사이트의 장점은 정적 Astro 사이트답게 client JavaScript가 매우 적다는 점이다.

리팩터링 후에도 유지한다.

## 일반 페이지

다음 페이지에서 불필요한 JS bundle을 추가하지 마라.

* About
* post list
* taxonomy
* archive
* 일반 Markdown post

Tailwind는 runtime JS를 필요로 하지 않아야 한다.

## Search

FlexSearch 관련 코드와 data는 Search 페이지에서만 필요하다.

## MDX

MDX를 사용한다는 이유만으로 client hydration을 추가하지 마라.

정적 Astro/MDX component는 정적으로 렌더한다.

`client:*` directive는 실제 interactive framework component가 필요한 경우가 아니면 사용하지 않는다.

## Link Preview

Astro Embed `LinkPreview`는 build-time static output으로 사용한다.

runtime metadata API를 만들지 않는다.

## iframe/embed

third-party iframe은 lazy loading을 사용한다.

iframe/embed가 존재하지 않는 post에서는 해당 third-party 비용이 없어야 한다.

## 이미지

기존 Astro image pipeline을 유지한다.

* Content Collection `image()`
* responsive image
* width/height
* lazy loading
* appropriate priority for hero/thumbnail
* WebP 등 기존 최적화

# 29. Git 작업

가능하면 `main`에서 직접 대규모 작업하지 말고 feature branch를 만든다.

예:

```text
feature/maintenance-refactor
```

정확한 이름은 자연스럽게 선택해도 된다.

금지:

* force push
* history rewrite
* 기존 main commit 삭제

작업 완료 후:

1. 모든 local validation 통과
2. git diff 최종 검토
3. 불필요한 파일이 남지 않았는지 확인
4. commit
5. push
6. branch CI 성공 확인
7. 프로젝트의 기존 workflow에 맞게 main에 merge
8. main의 `Verify and deploy` workflow 확인
9. build 성공 확인
10. deploy 성공 확인

GitHub mutation 권한이나 Codex 환경 제한 때문에 merge/CI 확인을 수행할 수 없다면 수행한 척하지 말고 정확히 어디까지 완료됐는지 보고한다.

# 30. 완료 조건

다음 조건이 모두 충족되어야 완료다.

* Tailwind가 실제 primary styling system
* `global.css`가 Tailwind import/theme 중심으로 최소화
* `@tailwindcss/typography` 미사용
* Markdown rendered elements도 Tailwind 기반 styling
* article + TOC 전체가 가운데 정렬
* `.md` 지원
* `.mdx` 지원
* `@astrojs/mdx` 정상 구성
* custom directive 완전 제거
* `remark-directive` 제거
* custom YouTube UI 제거
* `YouTubeEnhancement` 제거
* 공식 iframe/embed 직접 사용 가능
* generic Embed provider framework 없음
* Astro Embed `LinkPreview` 사용
* custom link-preview proxy/API 없음
* Pagefind 제거
* FlexSearch 도입
* 모든 콘텐츠 text 대상 substring 검색
* `down → Markdown` 동작
* Search dependency는 Search 페이지에 격리
* root `scripts/` 삭제
* `public/scripts/search.js` 제거
* 테스트 entry는 `tests/**/*.test.ts`
* `.spec.ts` 없음
* custom MJS test runner 없음
* ESLint 구성 완료
* Prettier 구성 완료
* Husky 구성 완료
* lint-staged 구성 완료
* format/lint가 pre-commit에서 정상 동작
* CI에 format/lint/check/test/build/browser validation 포함
* SEO 회귀 없음
* 접근성 회귀 없음
* image optimization 회귀 없음
* GitHub Pages base path 정상
* responsive layout 정상
* 문서가 실제 구조와 일치
* 불필요한 dependency 제거
* final build 성공
* browser tests 성공
* 최종 CI 성공
* main deployment 성공

4. Session / CSRF 구조 최종 변경
================================================================

중요한 최종 결정:

CSRF cookie를 완전히 제거한다.

브라우저 cookie는 session cookie 하나만 사용한다.

session cookie:
- HttpOnly
- Secure
- SameSite=Strict
- Path=/
- 7일
- raw 256-bit opaque random token

D1 sessions:
- raw token 저장 금지
- SHA-256 token hash 저장
- csrf_token 저장
- user_id
- created_at
- expires_at

CSRF token:
- cookie에 저장하지 않는다.
- JavaScript가 document.cookie에서 읽지 않는다.
- 보호된 GET에서 D1 session을 이미 읽으므로,
  req.user/session의 csrf_token을 EJS hidden input으로 출력한다.

예:

<input type="hidden" name="csrf" value="<%= user.csrf_token %>">

보호된 POST:
1. session HttpOnly cookie 읽기
2. D1 session hash lookup
3. user.status === active 확인
4. request body의 csrf와 D1 session.csrf_token 비교
5. exact Origin 확인
6. mutation 실행

CSRF token은 인증 credential 자체는 아니지만
URL/query/log 등에 흘리지 않는다.

삭제할 코드:
- csrfCookie()
- Login 시 csrf Set-Cookie
- Logout 시 csrf cookie clear
- document.cookie에서 csrf 값을 읽는 frontend 코드

Public GET:
session DB read 0 유지.

7. Invalid / expired session cookie 정리
================================================================

public GET에서는 session DB를 읽지 않는 기존 원칙 유지.

하지만 protected route에서 loadSession을 수행했을 때:

- session cookie가 존재함
- D1 session이 없음 / 만료됨 / inactive user임

이면:
- session cookie를 즉시 expire
- req.user = null

GET protected page:
Login으로 redirect 가능.

POST protected request:
401/403 등 기존 error 정책에 맞게 거부.

핵심:
한 번 protected route에서 invalid session임이 확인된 뒤에는
브라우저에 stale session cookie가 계속 남아
Navigation이 영구적으로 Profile을 표시하지 않게 한다.

Navigation 자체는 여전히
cookie 존재 여부만 보고 Login/Profile을 결정한다.
public request에서 D1 조회 금지.

8. PBKDF2 최종 정합성 수정
================================================================

Cloudflare Workers runtime에서 실제 동작하는 기준으로
PBKDF2-HMAC-SHA-256 iteration은 100,000으로 통일한다.

반드시 동일하게 수정:
- src/services/security.js
- development seed
- test fixture
- integration test expected value
- README
- docs/DECISIONS.md
- docs/IMPLEMENTATION_REPORT.md
- docs/MAINTENANCE.md
- 기타 600,000이라고 적힌 현재 문서

salt:
user별 random 16 bytes 유지.

password_iterations column:
유지.

기존 row별 iteration 값을 사용해 verify하는 구조도 유지.

production에 password_iterations > 100000인 test/sample account가 존재하는지 확인한다.
실제 사용자 데이터를 임의 삭제하지 않는다.
test/sample 데이터라면 현재 운영 정책에 맞게 정리하고 보고한다.

문서에서 600,000이라고 거짓으로 보고하지 않는다.

15. Pagination 최종 UX
================================================================

Pagination은 결과가 한 페이지뿐이어도 항상 표시.

1페이지:

<< < 1 > >>

2~3페이지:

<< < 1 2 3 > >>

등.

숨기지 않는다.

의미:

<<
실제 첫 페이지.

<
이전 10-page block.

숫자
현재 block의 실제 page.

>
다음 10-page block.

>>
실제 마지막 페이지.

10-page block 정의:

1~10
11~20
21~30
...

예:
현재 3페이지에서 > 클릭
3 + 10 = 13으로 가는 것이 아님.

11페이지로 이동.
즉 11~20 block을 보여줌.

현재 13페이지에서 < 클릭:
10페이지로 이동.
즉 이전 1~10 block으로 돌아감.

현재 13페이지에서 > 클릭:
21페이지.

현재 27페이지이고 total 27:
>>는 27.

항상 표시하되 이동할 수 없는 control은
링크를 숨기지 않는다.

예 current=1, last=1:

<< < 1 > >>

<<, <, >, >>는 disabled representation.

권장:
<span aria-disabled="true">...</span>

href="#" 사용 금지.

현재 page:
aria-current="page".

Post pagination과 Search pagination 모두 동일 component 사용.

16. Pagination invalid page 수정
================================================================

현재 /posts?page=999 같은 요청에서
pager만 last로 clamp되고 DB OFFSET은 999 기준이 되는 문제 수정.

Search도 동일.

규칙:
- page < 1 -> canonical page 1
- page > actual last -> actual last로 303 redirect
- last가 1이면 page=1 canonical
- query filter는 redirect에서 그대로 유지

Search:
all current filters를 URLSearchParams로 보존.

DB query와 pager가 서로 다른 page를 가리키지 않게 한다.

정상 request의 query round-trip은 불필요하게 늘리지 않는다.


================================================================
17. Search 날짜 최종 semantics
================================================================

Search form의 To 날짜는 사용자가 보는 의미대로 inclusive.

예:

from=2026-12-01
to=2026-12-31

이면:
12월 31일 전체 포함.

내부 SQL:
published_at >= 2026-12-01 00:00 KST
published_at <  2027-01-01 00:00 KST

즉 server에서 to 입력 날짜의 다음 날 00:00 KST를
exclusive upper bound로 계산.

Archive month link도 이 public semantics에 맞춘다.

예 2026년 9월:

/search?from=2026-09-01&to=2026-09-30

처럼 실제 마지막 날짜를 canonical query로 사용.

기존:
to=다음 달 1일
public 표현과 혼용하지 않는다.

21. Search SQL도 가능한 한 static query 파일
================================================================

Search 때문에 .sql 파일 안에 다시 복잡한 string interpolation을 만들지 않는다.

반복 Series/Category/Tag filter는
JSON array parameter + SQLite json_each(?)를 활용해
고정 SQL로 작성하는 방식을 우선.

예 개념:

Series:
json_each(series_json)

Category:
selected category 수와 relation count 비교

Tag:
wanted tag JSON array의 각 값이 posts.tags json_each에 존재하는지 검사

q:
FTS와 LIKE는 서로 다른 static SQL 파일 사용 가능.

Count/results:
각각 별도 query.

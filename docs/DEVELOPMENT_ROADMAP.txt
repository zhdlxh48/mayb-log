# `mayb-log` 개발 사양서 / 구현 로드맵

## 0. 프로젝트 목표

GitHub Repository `zhdlxh48/mayb-log`에 Astro 기반 개인 블로그를 처음부터 구축한다.

블로그는 다음 특성을 가장 중요하게 생각한다.

> **문서 중심의 옛 웹처럼 빠르고 직접적이되, 모든 게시물을 Series·Category·Tag·Date라는 현대적인 데이터 인덱스로 탐색할 수 있는 개인 아카이브.**

디자인 레퍼런스의 성격은 다음을 조합한다.

* Hacker News의 장식 없는 정보 중심 구조
* GeekNews의 현대적인 가독성과 적당한 여백
* 2chan/5ch 계열의 분류를 숨기지 않고 한눈에 보여주는 정보 밀도
* 현대적인 semantic HTML, responsive design, accessibility
* JavaScript 최소화
* 정적 HTML 우선
* SEO 우선
* GitHub Pages에서 매우 가볍게 제공 가능해야 함

시각적 밀도는 **GeekNews 정도의 여유를 기본으로 한다.**

# 1. 핵심 기술 스택

다음 기술을 사용한다.

```text
Astro
├─ TypeScript strict
├─ Tailwind CSS 4
│  └─ official @tailwindcss/vite integration
│
├─ Astro Content Collections
│  ├─ posts
│  ├─ authors
│  ├─ series
│  └─ pages
│
├─ Markdown
│  ├─ Astro built-in GFM
│  ├─ Astro built-in Shiki
│  ├─ remark-directive
│  └─ custom remark directive plugin
│
├─ Astro Assets / Image
│  └─ built-in Sharp image service
│
├─ Pagefind
├─ @astrojs/sitemap
├─ @astrojs/rss
│
└─ GitHub Actions
   └─ GitHub Pages
```

React, React Router, shadcn/ui 등은 사용하지 않는다.

Astro 컴포넌트와 native HTML/CSS/JS로 해결할 수 있는 것은 모두 그렇게 구현한다.

Astro는 Tailwind 4를 공식 Vite plugin 방식으로 사용하는 것을 현재 권장하므로 deprecated된 `@astrojs/tailwind` 방식은 사용하지 않는다. ([Astro Docs][1])

# 2. 의존성 원칙

필요 이상의 라이브러리를 설치하지 않는다.

예상되는 핵심 dependency는 다음 정도다.

```text
astro
@astrojs/sitemap
@astrojs/rss

remark-directive
unist-util-visit

sharp
```

개발 dependency:

```text
tailwindcss
@tailwindcss/vite

pagefind

typescript
@astrojs/check
```

Astro가 기본 제공하는 기능이 있으면 외부 라이브러리를 추가하지 않는다.

따라서 다음은 별도 설치하지 않는다.

```text
remark-gfm
shiki
react
date-fns
lodash
axios
clsx
UI component library
icon library
```

날짜 formatting은 특별한 이유가 없으면 `Intl.DateTimeFormat`을 사용한다.

아이콘은 정말 필요한 경우 작은 inline SVG를 사용한다.

# 3. 프로젝트 기본 경로

초기 GitHub Pages 주소는 project Pages로 가정한다.

```text
https://zhdlxh48.github.io/mayb-log/
```

Astro 설정:

```js
site: "https://zhdlxh48.github.io"
base: "/mayb-log"
```

모든 내부 URL, 검색 asset, RSS link, canonical URL이 `/mayb-log/` base path 환경에서 정상 작동하는지 반드시 테스트한다.

**절대로 다음처럼 root-relative URL을 곳곳에 하드코딩하지 않는다.**

```html
<a href="/posts/">
```

GitHub Pages에서는 이것이:

```text
https://zhdlxh48.github.io/posts/
```

를 가리키므로 잘못된 경로가 된다.

`import.meta.env.BASE_URL`, Astro URL API 또는 공용 URL helper를 사용한다.

Astro 공식 GitHub Pages 문서도 project repository에서는 repository 이름을 `base`로 설정하도록 요구한다. ([Astro Docs][2])

# 9. Thumbnail은 반드시 `image()`

`thumbnail`을 `string`으로 검증하지 않는다.

Content Collection의 공식 `image()` helper를 사용한다.

개념적으로:

```ts
schema: ({ image }) =>
  z.object({
    // ...
    thumbnail: image().optional(),
    thumbnailAlt: z.string().min(1).optional(),
  })
```

Astro `image()`는 해당 로컬 이미지가 유효한지 확인하고 `ImageMetadata`로 사용할 수 있도록 한다. ([Astro Docs][2])

다음 validation도 구현한다.

```text
thumbnail 존재
→ thumbnailAlt 필수

thumbnail 없음
→ thumbnailAlt 없어도 됨
```

# 10. 다른 스키마 validation

다음 조건을 반드시 검증한다.

### Series

```text
series 있음
→ seriesOrder 필수

series 없음
→ seriesOrder가 있으면 validation error
```

### 날짜

```text
updatedAt < publishedAt
→ validation error
```

### Authors

최소 1명.

```text
authors.length >= 1
```

### 제목/설명

빈 문자열 불가.

# 14. Taxonomy slug

Category와 Tag는 한국어도 사용할 수 있어야 한다.

slug 생성 시 한글을 삭제하거나 억지로 로마자로 변환하지 않는다.

Unicode-safe slug 함수를 작성한다.

규칙 예:

```text
NFKC normalize
trim
영문은 lowercase
공백 → -
문자 / 숫자 / 한글 / - 유지
나머지 특수문자 제거 또는 -
중복 - 병합
```

예:

```text
"Web Development"
→ web-development

"개인 개발"
→ 개인-개발
```

URL encode/decode가 안정적으로 동작해야 한다.

```yaml

```

게시글은 production build에서 완전히 제외한다.

다음 모든 곳에서 제외:

```text

Post list

```

개발 환경에서는 필요하다면 확인할 수 있게 만들어도 된다.

# 19. `noindex`

```yaml
seo:
  noindex: true
```

는 `draft`와 다르다.

페이지는 정상적으로 공개된다.

따라서:

```text
Sidebar/list
Pagefind
RSS
```

에는 포함해도 된다.

그러나:

```html
<meta name="robots" content="noindex,follow">
```

를 생성하며 sitemap에서는 제외한다.

# 20. Archive

`publishedAt`을 기준으로 자동 생성한다.

구조:

```text
ARCHIVE

2026              18
  09월              5
  08월              4
  07월              3

2025              20
  12월              5
  11월              3
```

연도는 최신 순.

월도 최신 순.

연도와 월 모두 클릭 가능하다.

```text
2026
→ /archive/2026/

09월
→ /archive/2026/09/
```

# 21. Timezone

사이트 기준 timezone을 설정한다.

초기:

```text
Asia/Seoul
```

날짜를 Archive로 grouping할 때 단순 UTC:

```ts
date.getUTCMonth()
```

같은 방식을 쓰지 않는다.

`Intl.DateTimeFormat`에 명시적으로:

```text
timeZone: "Asia/Seoul"
```

를 사용해서:

```text
year
month
day
```

를 계산한다.

날짜 표시도 동일한 timezone 기준으로 한다.

# 27. Mobile Navigation

모바일에서는 Sidebar를 항상 표시하지 않는다.

상단에 아주 작은 header:

```text

```

정도만 둔다.

`Index`는 native `<details>`/`<summary>`를 우선 사용한다.

초기 상태:

```text

```

를 보여준다.

Series / Category / Tag / Archive 각각도 필요하면 nested `<details>`로 접을 수 있다.

가능하면 이 UI 때문에 JavaScript를 추가하지 않는다.

```text
→ 불필요한 UI 제거

GeekNews
→ 한국어 가독성
→ 현대적인 line height
→ 적당한 여백

2chan / 5ch
→ 분류와 링크를 숨기지 않음
→ 데이터 밀도

현대 웹
→ responsive
→ accessibility
→ semantic HTML
→ CSS Grid/Flex
→ 올바른 metadata
```

결과적으로:

> **Old-web information density + modern typography/data structure**

가 되어야 한다.

# 55. Astro Image Pipeline 우선

별도 자체 Sharp CLI pipeline은 v1에서 만들지 않는다.

Astro built-in:

```text
astro:assets
Image
getImage
Markdown local images
Sharp service
```

를 최대한 활용한다.

Astro의 local `src/` 이미지는 optimization 대상이며 `<Image />` 기본 출력 포맷도 WebP이다. ([Astro Docs][3])

# 56. Image format

Raster image:

```text
JPEG
PNG
WebP
```

입력은 build 결과에서 가능하면:

```text
WebP
```

로 통일한다.

AVIF + WebP 두 포맷을 동시에 생성하지 않는다.

초기 버전에서는 WebP 단일 전략.

SVG:

```text
SVG 그대로
```

처리한다.

SVG를 억지로 WebP로 rasterize하지 않는다.

---

# 57. Image size

최대 long edge 목표:

```text
1600px
```

예:

```text
2400 × 1200
→ 최대 1600 × 800

2400 × 1800
→ 최대 1600 × 1200

1600 × 1000
→ 최대 1600 × 1000

1200 × 900
→ 1200 × 900
```

작은 이미지를 확대하지 않는다.

Astro responsive image의 `constrained`는 지정 크기나 원본 크기 이상으로 확대하지 않는 동작을 지원한다. ([Astro][4])

---

# 58. Responsive image breakpoint

Global image breakpoint는 필요 이상으로 많이 만들지 않는다.

권장:

```text
480
768
1024
1280
1600
```

원본보다 큰 variant는 만들지 않아야 한다.

Astro의 `image.breakpoints`와 `constrained` layout을 활용한다. ([Astro Docs][2])

---

# 59. WebP quality

초기 버전:

```text
quality: 80
effort: 6
```

정도를 기본으로 사용한다.

Astro 6 계열의 built-in Sharp service는 WebP encoder의 기본 `quality`, `effort`, `alphaQuality` 등을 image service config에서 지정할 수 있다. ([Astro Docs][5])

초기에는 file byte size를 강제하지 않는다.

---

# 60. Quality 최소값 60 정책

현재 v1은 adaptive compression을 사용하지 않으므로:

```text
quality = 80 fixed
```

이다.

향후 목표 용량 기반 adaptive compression을 구현한다면:

```text
quality upper = 80~82
quality minimum = 60
```

을 반드시 지킨다.

```text
quality < 60
```

으로 압축하지 않는다.

그리고 파일 크기를 맞추기 위해 이미지의 최대 크기를 1600 이하로 추가 축소하는 로직도 넣지 않는다.

즉 미래 custom service가 생겨도:

```text
1600 유지
quality >= 60
용량 초과 허용
```

가 정책이다.

---

# 61. 목표 byte size는 v1에서 제외

예:

```text
500KiB 이하
```

같은 target size는 Astro 기본 Image Service가 직접 제공하는 기능은 아니다.

이를 정확히 하려면 Custom Local Image Service를 구현해야 한다.

Astro는 이를 위한 공식 Image Service 확장 API를 제공하지만 초기 버전에서는 복잡도를 위해 사용하지 않는다. ([Astro Docs][6])

실제 운영 후 필요한 경우에만 추가한다.

# 75. robots.txt 주의

현재 사이트가:

```text
zhdlxh48.github.io/mayb-log/
```

처럼 origin의 subpath에 있으므로 `/mayb-log/robots.txt`는 origin root의 표준 `/robots.txt`를 대신할 수 없다.

따라서 초기 project Pages 환경에서는 robots.txt에 SEO를 의존하지 않는다.

중요한 제어는:

```text
meta robots
canonical
sitemap
```

에서 한다.

향후 custom domain 또는 `zhdlxh48.github.io` root site를 사용하면 root robots.txt를 제대로 관리할 수 있도록 구조를 바꾸기 쉽게 만든다.

# 113. 최종 Acceptance Criteria

프로젝트는 다음 조건을 모두 만족해야 완료로 간주한다.

* `/`가 About이다.
* Desktop에는 항상 왼쪽 Index Sidebar가 있다.
* Mobile에서는 Index가 기본적으로 접혀 있다.
* Sidebar에서 Series, Category, Tag, Archive를 한눈에 볼 수 있다.
* Sidebar에 게시글 제목 자체는 나열하지 않는다.
* `전체 글 보기`가 존재한다.
* 날짜 Archive는 `년도 → 월` 계층이다.
* 모든 taxonomy filter는 별도 static URL이다.
* Post list는 List/Grid 전환 가능하다.
* 기본은 List다.
* 선택한 view는 `localStorage`에 저장된다.
* Thumbnail 없는 글도 자연스럽다.
* 홈페이지나 목록에 Hero section이 없다.
* 카드 기반 SaaS UI처럼 보이지 않는다.
* GeekNews 정도의 readability가 있다.
* JavaScript가 없어도 기본 콘텐츠 탐색이 가능하다.
* Post thumbnail은 Content Collection `image()`다.
* 원본 이미지는 Git repository에 보관된다.
* build 결과 이미지는 Astro Image Pipeline을 이용한다.
* WebP 중심이다.
* 최대 responsive breakpoint는 1600px다.
* 작은 원본은 확대하지 않는다.
* WebP 기본 quality는 80 정도다.
* 향후 adaptive compression을 만들더라도 quality 60 미만은 사용하지 않는다.
* AVIF variant는 만들지 않는다.
* SVG는 SVG로 유지한다.
* Thumbnail이 없으면 OG image도 없어도 된다.
* Markdown 확장은 remark-directive 중심이다.
* React는 없다.
* Pagefind는 Search 페이지에서만 client JS를 사용한다.
* Sitemap/RSS가 생성된다.
* Post에 BlogPosting JSON-LD가 있다.
* canonical URL이 정확하다.
* `/mayb-log/` base path에서 asset/link/search가 깨지지 않는다.
* `draft`가 production에서 완전히 제외된다.
* 잘못된 content/directive는 build가 실패한다.
* `main` push 시 GitHub Actions가 Pages를 배포한다.

# 115. 구현 중 API가 달라진 경우

이 문서의 의도와 현재 공식 API가 충돌한다면:

1. 최신 stable Astro 공식 문서를 확인한다.
2. preview/canary API는 사용하지 않는다.
3. 최신 stable API로 동일한 기능을 구현한다.
4. deprecated API는 사용하지 않는다.
5. 기능적 사양은 유지한다.

현재 문서 기준으로 Astro는 `src/content.config.ts`의 `defineCollection()`/`glob()` 방식, schema callback의 `image()`, built-in Sharp image service, responsive `image.layout`/`image.breakpoints`를 지원한다. ([Astro Docs][2])

문서 목적
---------
현재 Astro + Tailwind + 정적 Markdown 빌드 기반 블로그를 다음 철학과 구조로 재설계한다.

핵심 철학:
- HTML이 데이터와 문서 구조를 설명한다.
- CSS는 의미 있는 class 이름을 기준으로 최소한의 표현만 담당한다.
- JavaScript는 필요한 상호작용에만 사용한다.
- 콘텐츠 변경은 애플리케이션 전체 rebuild/deploy와 분리한다.
- Markdown이 작성/수정의 canonical source다.
- 글 저장 시 Markdown을 HTML과 검색용 plain text로 변환해서 D1에 저장한다.
- 공개 페이지 요청 시 Markdown parser를 실행하지 않고 저장된 HTML을 즉시 렌더링한다.
- 서버는 Cloudflare Workers 자체를 사용하며 Express/Fastify/Koa/ASP.NET/Go 별도 서버를 두지 않는다.
- 데이터는 Cloudflare D1, 이미지/업로드 파일은 R2, CSS/JS/vendor 파일은 Workers Static Assets에 둔다.
- 가능한 한 framework와 runtime dependency를 줄이고, 브라우저 표준과 Cloudflare primitive를 우선한다.
- public 사이트는 옛 문서형 웹의 raw HTML 감각과 현대적인 데이터 구조를 결합한다.
- Grid view와 LinkPreview는 제거한다.
- Sidebar를 제거하고 상단 navigation을 사용한다.
- Series / Categories / Tags / Archive는 상단 메뉴에서 native HTML Popover API를 우선 사용해 펼쳐볼 수 있게 한다.

10. Markdown canonical storage
--------------------------------------------------------------------------------

글 작성/수정 기준은 Markdown이다.

DB에 최소:
- body_markdown
- body_html
- body_text

를 저장한다.

body_markdown:
- canonical source
- 수정 화면 textarea에 다시 로드

body_html:
- Worker가 저장 시 Marked로 생성
- 공개 page에서는 이것을 그대로 사용
- 공개 request 시 Markdown parse하지 않음

body_text:
- 검색용 plain text
- 저장 시 HTML/Markdown에서 생성
- normalize해서 검색에 사용

브라우저의 preview HTML을 server가 신뢰하지 않는다.

Admin browser:
Markdown -> Marked -> preview

Save:
Markdown -> Worker
Worker -> Marked -> canonical body_html
Worker -> plain text -> body_text
Worker -> D1 INSERT/UPDATE

12. Raw HTML in Markdown 보안 정책
--------------------------------------------------------------------------------

회원가입/다중 user가 생기므로 모든 active user가 arbitrary <script>를 public article에 삽입할 수 있게 하면 안 된다.

초기 구현 원칙:
- 일반 author role의 Markdown에서는 raw HTML을 escape/비활성 처리한다.
- Markdown 표준 기능만으로 글을 작성하게 한다.
- 일반 link/image/code/table/blockquote/details 등 필요한 기능은 Markdown 또는 안전한 별도 문법으로 처리한다.
- arbitrary script/event handler/javascript: URL을 허용하지 않는다.

admin-only raw HTML이 정말 필요하다면 추후 별도 명시 기능으로 추가한다.
이번 v1에서 regex sanitizer를 직접 만들지 않는다.

공개 article body에 user-provided arbitrary script가 실행되도록 구현하지 않는다.

--------------------------------------------------------------------------------
16. users table
--------------------------------------------------------------------------------

예시:

CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  username TEXT NOT NULL UNIQUE,
  display_name TEXT NOT NULL,

  password_hash TEXT NOT NULL,
  password_salt TEXT NOT NULL,
  password_iterations INTEGER NOT NULL,

  role TEXT NOT NULL DEFAULT 'author'
    CHECK (role IN ('admin', 'author')),

  status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'active', 'inactive')),

  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

규칙:
- username은 login ID
- username은 가입 후 immutable하게 유지하는 것을 권장
- username은 URL/account identifier로 사용 가능
- display_name은 public author name
- password plaintext 저장 금지
- pending이 default
- active만 login 가능
- inactive 로그인 불가
- role default author

username 제안 validation:
- 3~32 chars
- lowercase ASCII
- [a-z0-9_-]
- 입력은 trim + lowercase normalize
- display_name은 Unicode 허용

password:
- 최소 12자 권장
- 최대 128자 정도로 제한해 abuse 방지
- arbitrary "대문자 1개, 기호 1개" 규칙은 강제하지 않는다.

--------------------------------------------------------------------------------
17. user status 동작
--------------------------------------------------------------------------------

상태 의미:

pending:
- signup 직후 기본
- 로그인 불가
- admin 승인 대기

active:
- 로그인 가능
- role에 따라 작성/관리 가능

inactive:
- 로그인 불가
- 기존 session 즉시 revoke
- 작성한 public post는 삭제하지 않음

admin user 관리 화면:
- /admin/users
- Pending
- Active
- Inactive
분류
- status 변경
- 필요하면 role 변경

status 변경은 admin만 가능.

active -> inactive:
- 해당 user의 모든 sessions 즉시 삭제

inactive -> active:
- 다시 login 가능
- 기존 session은 복원하지 않음
- 새 login 필요

pending -> active:
- 승인

pending -> inactive:
- 거절/차단 용도

login 실패 메시지는:
"ID 또는 비밀번호가 올바르지 않거나 로그인할 수 없는 계정입니다."
처럼 status를 외부에 구체적으로 노출하지 않는다.

--------------------------------------------------------------------------------
20. password hashing
--------------------------------------------------------------------------------

D1에 plaintext password 저장 금지.

Cloudflare Workers Web Crypto를 사용한다.

기본 방식:
PBKDF2-HMAC-SHA-256
+ user별 cryptographically random salt
+ 충분한 iteration count

password_salt:
- 최소 16 bytes random
- DB에는 base64/base64url encoding

password_hash:
- derived bits
- DB에는 base64/base64url

password_iterations:
- row에 저장
- 향후 work factor 증가 시 기존 user도 검증 가능

정확한 iteration 수는 구현 당시 Workers 환경에서 benchmark하고 문서화한다.
너무 낮은 값을 임의로 사용하지 말고,
보안 권고 수준과 Worker 응답/CPU 제한 사이를 측정해 결정한다.

login 성공 후 기존 iteration 수가 current policy보다 낮으면
가능한 경우 password를 current work factor로 재hash한다.

hash compare는 timing-safe comparison을 사용한다.

25. sessions table

권장 SQL:

CREATE TABLE sessions (

  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  csrf_token TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

CREATE INDEX sessions_user_id_idx ON sessions(user_id);

session raw token:
- crypto.getRandomValues()
- 최소 256-bit entropy

Browser cookie:
raw session token

D1:
SHA-256(raw session token)

DB dump만으로 즉시 session hijack이 어렵도록 raw token을 DB에 저장하지 않는다.

================================================================================
보안 구현 참고 메모
================================================================================

- Cloudflare Turnstile은 client widget만으로 완료되는 기능이 아니다.
  signup/login POST에서 Worker가 Siteverify API를 반드시 호출한다.
- Turnstile token은 짧은 유효기간 및 single-use 특성이 있으므로 재시도 UX를 고려한다.
- D1은 foreign key constraint를 지원하므로 user/post/session 관계를 실제 FK로 정의한다.
- Workers Web Crypto의 PBKDF2, SHA-256, crypto.getRandomValues, timing-safe comparison을 우선한다.
- 비밀번호, raw session token, Turnstile secret을 로그에 남기지 않는다.
- approved active author의 콘텐츠라도 arbitrary script execution을 기본 허용하지 않는다.

================================================================================
최종 핵심 요약
================================================================================

이 프로젝트의 최종 방향은 "정적 사이트 생성기 기반 블로그"가 아니라
"Cloudflare가 서빙하는 작은 동적 문서 시스템"이다.

콘텐츠:
Markdown -> Save -> HTML/Text -> D1

공개 요청:
D1 -> stored HTML -> semantic HTML response

회원:
Signup + Turnstile -> pending
Admin approval -> active
inactive -> login/session 차단

작성자:
logged-in user.id -> content.author_user_id

인증:
Password hash + D1 session + HttpOnly cookie + CSRF
JWT 없음

Frontend:
HTML + CSS + htmx
Marked/Prism/browser-image-compression는 필요한 route에만 사용

서버:
Cloudflare Workers
별도 Express/Fastify/ASP.NET/Go 서버 없음

데이터:
최소 table 구조를 유지하되,
users/sessions/content/series의 실제 관계는 D1 foreign key로 명확히 보장한다.
